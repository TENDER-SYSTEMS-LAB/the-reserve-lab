# THE RESERVE — 현재 설계 감사 · 세계관 설계 범위 결정 · 다음 작업 로드맵

## 역할과 목표

너는 TENDER SYSTEMS 세계관 안에서 개발 중인 작품 **THE RESERVE**의 설계 검토자이자 작업 계획 파트너다.

실제 저장소와 제공된 대화·문서를 확인하여 다음 질문에 답해줘.

> THE RESERVE는 지금 어디까지 설계되었는가? 이 작품이 성립하려면 세계관을 어디까지, 얼마나 깊게 설계해야 하는가? 그 목표와 현재 상태의 차이를 메우려면 다음에 무엇을 어떤 순서로 해야 하는가?

작업은 반드시 **현재 상태 확인 → 필요한 설계 범위와 깊이 결정 → 설계 공백 분석 → 실행 가능한 로드맵** 순서로 진행해줘. 기능 목록부터 만들거나, 세계관을 무한히 확장하는 브레인스토밍으로 대체하지 마.

이번 요청은 **조사·분석·계획 수립**이다. 저장소 수정, Wiki 기록, 이슈 생성, 구현, 커밋, 푸시는 하지 마. 네가 추천하는 방향은 검토용 제안이며, 사용자가 확정한 설정으로 기록하지 마.

답변과 최종 보고서는 한국어로 작성해줘.

## 1. 프로젝트 맥락과 조사 출발점

### 1.1 작품 맥락

TENDER SYSTEMS는 쉽게 측정·가격화·소유·저장·교환하기 어려운 것을 정교한 제도와 시스템으로 다루는 작품 세계관이다. 인간적인 대상과 계산적이고 건조한 기관의 작동 방식 사이의 대비가 중요하다.

THE RESERVE는 은행과 관련된 별도 작품으로 논의되어 왔다. 그러나 **은행을 소재로 한다는 사실만으로 예금은행, 중앙은행, 통화 발행기관, 보관기관, 신용기관 중 하나라고 단정하면 안 된다.** 무엇을 하는 기관인지부터 실제 기록을 확인해야 한다.

관련 작품은 다음과 같다. 아래 설명은 탐색을 위한 맥락이며, 최신 설계와 역할 경계는 해당 기록에서 확인해줘.

- **OTHER GOODS**: 소유하거나 상품화하기 어려운 것을 상업과 상품의 형식으로 다루는 작품.
- **LONGING RESEARCH**: 인간의 실천과 경험 등의 가치 변화를 연구하고 가격·시장 언어로 다루는 작품. 저장소나 과거 문서에는 LONGING으로 표기될 수 있다.
- **THE RESERVE**: 위 작품들과 구별되는 은행 관련 제도와 경험을 탐색하는 작품. 보관·신뢰·약속·시간·의무·신용은 검토 대상이지, 모두 채택된 기능이 아니다.

### 1.2 확인된 조사 출발점

2026-09-06에 확인한 THE RESERVE Wiki의 출발 정보는 다음과 같다. 실행 시 최신 기록으로 다시 검증해줘.

- 공식 작품명은 **THE RESERVE**다.
- 공식 bio는 **“A place for what remains.”**다.
- 다른 작품과 세계관은 공유하지만 공개 문구까지 반복하지 않는다. THE RESERVE의 bio에 `other`나 `changing values`를 재사용하지 않는다.
- 기관 유형과 금융 메커니즘은 검토 중이며, `future claims`는 기존 LLM의 추천이지 사용자가 채택한 설계가 아니다.
- `RS-001`, `@thereserve.rs001`, 상품, 수식, 담보, 채무불이행의 결과, 실시간 작동, 공유 통화 인프라는 위 확인 시점에 확정되지 않았다.
- 기존 은행 해석 기록에는 누락된 첨부 프롬프트에 대한 참조가 있다. 그 응답 전체를 사용자의 의도나 확정 요구사항으로 간주하면 안 된다.

특히 **bio의 “what remains”를 근거로 보존기관이 확정되었다고 추론하지 마.** 반대로 과거 LLM이 신용 모델을 추천했다는 이유로 그것이 현재의 중심 설정이라고 단정하지도 마.

## 2. 먼저 실제 기록을 조사해줘

### 2.1 읽기 순서

저장소의 최신 `AGENTS.md`를 먼저 확인하고, 다음 순서로 조사해줘.

1. `wiki/index.md`
2. `wiki/current-state.md`
3. `schema.md`
4. 이번 작업과 관련된 개념·결정·질문 문서
5. 판단 근거가 부족하거나 충돌이 있을 때 해당 원문과 변경 이력

확인 시점에 존재했던 주요 관련 문서는 다음과 같다. 이름이 바뀌었다면 최신 인덱스에서 대응 문서를 찾아줘.

- `wiki/overview.md`
- `wiki/concepts/institutional-directions.md`
- `wiki/concepts/future-claims.md`
- `wiki/questions/Q-001-institutional-scope.md`
- `wiki/decisions/DEC-001-project-name.md`
- `wiki/decisions/DEC-002-public-language.md`
- `wiki/log.md`
- `raw/sources.md`

처음부터 모든 raw 자료를 무차별적으로 읽지 마. Wiki에서 논점을 파악한 뒤 중요한 판단에 필요한 원문을 확인해줘. 관련 저장소는 공통 철학, 통화, 역할 경계, 의존성을 검증하는 범위에서 읽어줘.

### 2.2 증거와 상태를 구분하는 원칙

다음 구분을 유지해줘.

- 사용자가 명시적으로 확정한 결정.
- 함께 논의하고 있지만 아직 확정하지 않은 방향.
- LLM만 제안한 아이디어나 해석.
- 의도적으로 보류한 사항과 폐기·대체된 사항.
- 아직 조사하지 못한 사항, 접근하지 못한 사항, 조사 범위에서 기록을 찾지 못한 사항.
- 이번 검토에서 새로 제안하는 내용.

저장소에 상태와 출처 체계가 있다면 그것을 존중해줘. 특히 문서의 `working` 상태나 반복 등장만으로 사용자 승인을 추정하지 마.

판단이 충돌하면 원문의 발언 주체, 실제 결정 시점, 명시적 승인 여부를 확인해줘. 문서의 최근 수정일만으로 우선순위를 정하지 마. 해결되지 않은 충돌은 양쪽 근거와 함께 남겨줘.

각 주요 판단에는 저장소·문서 경로와 가능하면 섹션, 소스 ID, 링크 또는 커밋을 붙여줘. 조사 기준일과 조회한 브랜치·커밋도 확인 가능한 범위에서 기록해줘.

접근하지 못한 자료가 있더라도 전체 분석을 중단하지 마. 확인한 범위와 한계를 밝히고, 가능한 부분의 보고서와 조건부 로드맵을 작성해줘. **“기록을 찾지 못했다”와 “한 번도 논의되지 않았다”를 같은 뜻으로 사용하지 마.**

## 3. 현재 설계 상태를 감사해줘

지금까지의 설계를 재서술하는 데 그치지 말고, 실제로 다음 단계에 사용할 수 있는 수준인지 판단해줘.

다음 영역을 중심으로 조사하되, 작품에 적용되지 않는 항목은 그 이유를 적어줘.

| 검토 영역 | 확인할 내용 |
| --- | --- |
| 작품의 핵심 | 중심 질문, 대비, 관객에게 남기려는 경험, 이 작품이 별도로 존재해야 하는 이유 |
| 기관의 정체 | 무엇을 하는 기관인지, 누구를 위해 작동하는지, 권한과 한계는 무엇인지 |
| 취급 대상 | 무엇을 받고·보관하고·평가하고·발행하고·빌려주는지, 대상과 기록·권리의 차이 |
| 제도와 규칙 | 자격, 계약, 권리·의무, 시간, 수수료·금리 등 적용 가능한 운영 규칙 |
| 결과와 위험 | 관객의 선택으로 달라지는 것, 손실·거절·미이행·회복의 가능성과 범위 |
| 통화와 수량 | 무엇을 어떤 단위로 표현하는지, 가격·잔액·청구권·통화가 구분되는지 |
| 관객 경험 | 방문부터 참여·결과 확인·퇴장·재방문까지의 흐름과 실제 상호작용 |
| 공통 세계관 | TENDER SYSTEMS 및 다른 작품과의 관계, 공유해야 할 것과 독립시킬 것 |
| 공개 표현 | 확정된 이름·bio, 기관 언어, UI·문서·계정 등 접점과 노출 수준 |
| 구현과 운영 | 실제 코드·프로토타입·테스트의 존재 여부, 상태 저장, 시간 처리, 유지관리 |

감사 결과는 다음 열을 갖는 표로 정리해줘.

`영역 / 현재 기록된 내용 / 결정 상태·발언 주체 / 설계 구체성 / 구현 증거 / 남은 공백 / 근거`

**설계의 구체성, 사용자 승인 여부, 구현 여부는 서로 다른 축이다.** 상세한 LLM 제안이 존재해도 미승인일 수 있고, 승인된 개념이 있어도 구현은 없을 수 있다. Wiki가 존재한다는 이유로 기능이 구현되었다고 판단하지 마.

전체 진척도를 근거 없는 백분율로 표현하지 말고, “무엇까지 설명할 수 있고 무엇은 아직 결정할 수 없는가”로 요약해줘.

## 4. 세계관을 어디까지 설계할지 먼저 정해줘

이 작업의 핵심이다. 현재 비어 있는 항목을 모두 채우는 것이 목표가 아니다. **작품이 성립하는 데 필요한 설계와, 설정을 늘릴 뿐인 설계를 구별해줘.**

### 4.1 범위·깊이·노출·구현을 분리해줘

다음 네 가지를 혼동하지 마.

- **범위**: 기관 내부까지만 다룰지, 다른 작품과의 인프라까지 다룰지, 더 큰 경제·사회까지 다룰지.
- **깊이**: 한 줄 전제로 충분한지, 일관된 규칙이 필요한지, 계산·예외·검증까지 필요한지.
- **노출**: 관객이 반드시 알아야 할 것, 운영 화면이나 문서에서 발견할 것, 내부적으로만 정의할 것.
- **구현**: 실제 코드로 작동시킬 것, 정적 표현으로 충분한 것, 프로토타입에서 검증할 것.

관객에게 설명하지 않는다는 이유로 내부 규칙도 없어도 되는 것은 아니다. 반대로 내부 설정이 있다는 이유로 모두 화면에 설명할 필요도 없다.

### 4.2 설계 범위의 대안을 비교하고 하나를 추천해줘

다음 정도의 범위를 비교하되, 기존 기록에 더 적절한 구분이 있으면 조정해줘.

- **기관 중심**: THE RESERVE의 핵심 기능, 대상, 규칙, 관객 경험과 직접 필요한 주변 맥락.
- **공통 인프라 포함**: 기관 중심 설계에 더해 작품 간 단위·계정·정산·참조 관계 중 필요한 부분.
- **경제·사회 체계 포함**: 여러 기관, 발행 권한, 거시 흐름, 역사·사회적 맥락까지 연결한 설계.

각 대안이 만드는 작품적 이득, 추가 결정, 의존성, 유지관리 부담, 다른 작품과의 중복을 비교해줘. “작게 시작하는 것이 무조건 좋다”거나 “세계관이 클수록 좋다”는 전제를 두지 마.

**이번 로드맵에서 사용할 권장 범위를 하나 선택하고 이유를 제시해줘.** 다만 이를 사용자 확정으로 쓰지 말고, 계획 수립을 위한 권장안이라고 표시해줘.

기관 유형이 먼저 정해져야 범위를 결정할 수 있다면, 그 결정을 최우선 과제로 놓고 유형별로 달라지는 경계를 밝혀줘. 그렇더라도 선택지 나열이나 질문만으로 끝내지 말고, 가장 타당한 작업 가정을 정해 조건부 로드맵을 완성해줘.

### 4.3 영역별 목표 깊이를 정해줘

다음 척도나 동등하게 명확한 기준을 사용해줘.

| 깊이 | 필요한 설계 수준 |
| --- | --- |
| D0 | 이번 범위에서 설계하지 않는다. 불필요한 것인지 의도적으로 보류한 것인지 구분한다. |
| D1 | 존재와 역할, 핵심 전제만 정의한다. 상세 작동은 현재 경험에 필요하지 않다. |
| D2 | 정상 흐름, 권리·의무, 입력과 결과, 핵심 제약을 일관된 규칙으로 정의한다. |
| D3 | 상태 전이, 시간 처리, 필요한 계산, 주요 예외와 검증 사례까지 정의한다. |

최소한 기관 정체, 취급 대상, 운영 규칙, 시간과 결과, 통화·수량, 관객 경험, 다른 작품과의 연결, 외부 경제·역사, 공개 표현에 대해 아래 표를 작성해줘.

`영역 / 현재 깊이 / 목표 깊이 / 필요한 이유 / 관객 노출 범위 / 구현 필요성 / 여기서 멈추는 기준`

특정 은행 기능을 전제로 모든 항목을 D3로 올리지 마. 작품에 필요하다면 복잡하고 정교하게 설계하되, 복잡성의 이유와 적용 범위를 설명해줘.

### 4.4 세계관 설계의 완료 기준과 확장 조건을 정해줘

“더 이상 설정을 추가하지 않고 다음 단계로 넘어가도 되는 상태”를 구체적으로 정의해줘. 문서 수나 분량이 아니라 다음을 판단할 수 있어야 한다.

- 이 기관이 존재해서 가능해지는 행위와 결과가 무엇인지 설명할 수 있다.
- 관객의 핵심 행동이 어떤 규칙을 거쳐 어떤 상태 변화로 이어지는지 추적할 수 있다.
- 대표적인 정상·거절·예외 상황이 추가 설정을 즉석에서 만들지 않고 처리된다.
- 관객이 알 필요 없는 부분과, 제작자가 아직 결정하지 못한 부분이 구분된다.
- 다른 작품과 공유하는 약속이 필요한 범위에서 정의되고, 불필요한 의존성이 없다.

보류한 영역마다 다시 설계해야 하는 **구체적 촉발 조건**도 적어줘. “나중에 확장 가능”이라는 문장만으로 끝내지 마.

## 5. 목표 범위 안에서 반드시 검증할 쟁점

### 5.1 은행이라는 형식이 실제로 필요한가

은행의 외형을 입힌 시적 텍스트나 상품 목록만으로 끝나지 않도록 검토해줘.

이 기관이 어떤 권리·의무·신뢰·시간적 관계를 만들어내는지, 단순한 상점·기록보관소·리서치 기관과 무엇이 다른지 확인해줘. 은행의 모든 현실 기능을 재현할 필요는 없지만, 채택한 기능은 작품 안에서 일관되게 작동해야 한다.

`Memory Bank`, `Time Bank`, 감정 화폐 같은 익숙한 비유를 자동 해답으로 쓰지 마. 기존 제안을 먼저 평가하고, 무엇을 시적으로 맡길지보다 이 기관이 실제로 무엇을 하는지를 밝혀줘.

시스템의 부실함이나 임의적인 오류를 대비를 만드는 지름길로 사용하지 마. 운영 논리는 정교할 수 있지만, 그 제도가 다루는 대상과 제도 자체의 한계에서 어떤 긴장이 생기는지 검토해줘.

### 5.2 통화 설계가 어디까지 필요한가

통화 이름부터 추천하지 말고 다음을 구별해줘.

- 가격이나 양을 표시하기 위한 기준 단위.
- 계정 안의 잔액이나 기록.
- 다른 주체에 대한 청구권이나 의무.
- 실제로 이전·교환·정산되는 수단.
- 발행·회수·상환·준비자산 같은 추가 메커니즘.

이 구분 중 무엇이 THE RESERVE에 지금 필요한지, 무엇은 LONGING RESEARCH나 TENDER SYSTEMS의 공통 결정인지, 무엇은 유보할 수 있는지 판단해줘.

THE RESERVE가 통화 발행기관이라는 가정이나 세 작품이 같은 통화를 사용한다는 가정을 자동으로 추가하지 마. 통화가 필요하다고 판단하면 누가 무엇을 발행하고, 누가 무엇을 받아들이며, 어떤 행위에 쓰이는지까지 필요한 깊이를 제시해줘.

### 5.3 작품 간 연결과 독립성을 검증해줘

각 작품의 핵심 질문과 제도적 역할이 겹치지 않는지 확인해줘. THE RESERVE를 다른 작품의 결제 기능이나 세계관 설명 도구로만 축소하지 마.

공유가 필요하다면 단위 정의, 식별자, 참조 문서, 계정 또는 정산 규칙 등 구체적으로 무엇을 공유해야 하는지 적어줘. 함께 공개해야만 성립하는지, 독립 공개가 가능한지도 검토해줘.

### 5.4 관객의 행동으로 규칙을 검증해줘

권장 방향에 대해 핵심 상호작용 하나를 골라 다음 경로를 시험해줘.

`관객의 입력·선택 → 기관의 판단 → 적용되는 규칙 → 상태 변화 → 관객에게 보이는 결과`

정상 처리, 자격 미달·거절, 시간 경과, 중도 이탈·취소, 미이행이나 회복 등 **해당 방향에 실제로 관련된 대표 사례 3~5개**를 사용해줘. 적용되지 않는 사례를 위해 새 기능을 만들지 마.

이 검증은 완성된 시스템을 꾸며내기 위한 것이 아니다. 어떤 결정이 없어서 사례를 끝까지 설명할 수 없는지 드러내고, 그 공백을 로드맵에 반영하기 위한 것이다.

관객의 경험상 결과와 실제 생활상의 금전·개인정보 위험도 구분해줘. 실제 입출금, 외부 결제, 신용 제공, 민감정보 수집은 명시적 요구가 없다면 범위에 넣지 마.

## 6. 공백 분석과 의존성 기반 로드맵을 만들어줘

### 6.1 모든 빈칸을 작업으로 만들지 마

현재 상태와 목표 깊이를 비교하여 공백을 다음과 같이 나눠줘.

- 다음 판단을 막는 핵심 결정.
- 경험을 검증하기 전에 필요한 규칙.
- 프로토타입으로 먼저 시험할 불확실성.
- 구현과 공개 전에 해결할 사항.
- 의도적으로 남길 여백 또는 현 범위 밖의 설정.

정해진 목표 깊이에 도달하는 데 필요한 작업만 로드맵에 넣어줘.

### 6.2 단계와 통과 조건

조사 결과에 맞춰 단계 수를 정하되, 개념·기관 역할·운영 규칙·관객 경험·구현 검증 사이의 선후 관계가 보여야 한다.

각 단계에는 아래 항목을 포함해줘.

`단계 / 목표 / 주요 작업 / 선행 조건 / 산출물 / 완료·통과 기준 / 막히는 경우의 대안`

단순히 “세계관 정리 → 디자인 → 개발”이라고 쓰지 마. 예를 들어 기관 역할에 따라 취급 대상이 달라지고, 대상에 따라 원장이나 시간 규칙의 필요성이 달라지는 식으로 **실제 의존성**을 밝혀줘.

기관 유형에 무관하게 진행할 수 있는 공통 작업과, 유형 선택 후에만 가능한 조건부 작업도 나눠줘.

핵심 경험을 시험하는 가벼운 스케치·프로토타입은 세계관 전체 확정 전에 가능할 수 있다. 반면 검증되지 않은 가정을 실제 구현 명세처럼 고정하지 마. 필요한 경우 프로토타입 결과로 앞선 결정을 재검토하는 경로를 포함해줘.

임의의 마감일이나 개발 기간을 제시하지 마. 우선순위와 순서, 병렬 가능 여부, 상대적 부담과 불확실성으로 계획해줘.

### 6.3 바로 시작할 작업 3~5개

장기 로드맵과 별도로 다음 작업 세션에서 실제로 할 일을 3~5개 골라줘. 각 작업은 다른 에이전트에게 그대로 넘길 수 있게 작성해줘.

각 작업에는 다음 정보를 담아줘.

- 작업 ID와 구체적인 제목.
- 지금 해야 하는 이유와 선행 작업.
- 읽어야 할 실제 문서·근거.
- 답해야 할 핵심 질문과 수행할 행동.
- 만들어야 할 산출물과 포함할 내용.
- 완료 기준과 사용자의 판단이 필요한 지점.
- 이번 작업에서 하지 않을 것.

“통화 고민하기”, “세계관 구체화”, “UI 만들기”처럼 완료 여부를 판단할 수 없는 작업명은 피하고, 어떤 의사결정이나 검증 결과가 나와야 하는지 명확히 해줘.

새 문서가 필요하다면 기존 문서의 보완으로 충분한지 먼저 판단해줘. 새로운 경로는 제안임을 표시하고 실제 존재하는 파일처럼 적지 마. 문서나 빈 페이지를 늘리는 일을 성과로 취급하지 마.

## 7. 최종 보고서 구성

최종 답변은 다음 순서로 작성해줘. 같은 내용을 여러 절에서 반복하기보다 앞선 표와 판단을 참조해줘.

1. **핵심 결론**: 현재 단계, 권장 설계 범위·깊이, 가장 먼저 할 일.
2. **조사 범위와 근거**: 확인한 저장소·문서·기준 시점, 접근 한계와 누락 자료.
3. **현재 설계 감사**: 확정·미확정·LLM 제안·구현 증거·핵심 공백.
4. **세계관 설계 범위 권장안**: 대안 비교, 선택 근거, 영역별 목표 깊이, 노출·구현 구분.
5. **설계 완료 기준과 보류 경계**: 어디서 멈추고, 어떤 조건에서 다시 확장하는지.
6. **핵심 검증 결과**: 기관 역할, 통화의 필요 수준, 작품 간 경계, 대표 상호작용의 미해결점.
7. **의존성 기반 로드맵**: 단계별 산출물과 통과 기준, 공통·조건부 작업.
8. **바로 시작할 작업 3~5개**: 실행 가능한 작업 카드.
9. **사용자 결정이 필요한 쟁점**: 우선순위가 높은 최대 5개. 각 쟁점의 권장안과 달라질 작업을 함께 제시.

가능하다면 보고서를 독립적인 Markdown 파일로도 제공해줘. 파일명은 `THE_RESERVE_Design_Audit_and_Roadmap.md`로 해줘. 파일 생성 기능이 없다면 같은 내용을 하나의 Markdown 본문으로 제공해줘. 이 보고서는 검토용 산출물이며 저장소에 자동 등록하지 마.

## 8. 최종 원칙

- 기존 기록으로 해결할 수 있는 질문을 사용자에게 다시 묻지 마.
- 미확정 사항 때문에 전체 작업을 멈추지 말고, 근거와 가정을 구분하여 가능한 최선의 권장안을 제시해줘.
- 새 제안, 현실의 금융 설명, 세계관에서 선택하는 허구적 규칙을 구분해줘.
- 외부 금융 사실이 결론에 필요하면 공식 기관 등 1차 출처로 검증하고 출처를 붙여줘. 기존 LLM의 설명을 검증된 사실처럼 재사용하지 마. 불필요한 금융사·규제 조사로 범위를 넓히지도 마.
- 완성도와 단순함을 같은 뜻으로 쓰지 마. 필요한 정교함은 유지하되, 작품적 이유가 없는 복잡성은 추가하지 마.
- 기관처럼 건조하고 정밀한 공개 언어와 내부 분석 문서의 설명 방식을 구분해줘. 몰입감을 위해 실제 인허가나 금전적 권리를 허위로 주장하도록 제안하지 마.
- 운영자의 개인 신원을 보고서나 공개 문구에 불필요하게 넣지 마. 공개 주체는 TENDER SYSTEMS다.
- 이번에는 읽기와 분석만 수행해줘. 기존 원문, Wiki, 로그, 상태값을 수정하거나 네 권장안을 확정 결정으로 승격하지 마.

최종적으로 다음 문장을 구체적으로 완성할 수 있어야 한다.

> **THE RESERVE는 현재 ______까지 정해져 있다. 이번 단계에서는 ______까지 설계하되, ______는 의도적으로 남겨둔다. 따라서 다음 작업은 ______이며, 완료되었다고 판단할 기준은 ______다.**
